02 / Concepts that must not be confused

ConceptPurposeIn this pipeline
Key generationCreate initial secret material, typically from randomness.Wallet setup / mnemonic entropy.
Key derivationDeterministically derive keys from existing secret material.BIP-32 plus a path convention such as BIP-44.
Public-key cryptographyRelate a private key to a public key and support signatures.secp256k1.
HashingMap input data to a fixed-size digest.Keccak-256.
ChecksumHelp detect common transcription errors.EIP-55.
EncodingRepresent data in a specified textual format.Hexadecimal; EIP-55 casing convention.

03 / The derivation path

m/44'/60'/0'/0/0

  • m: master node.
  • 44': BIP-44 purpose.
  • 60': registered coin type for Ethereum.
  • 0': account index zero.
  • 0: external/receiving chain.
  • 0: first address index.

Wallets may support different paths or account models. This is a common Ethereum path, not a universal guarantee for every wallet.

04 / Historical context

Approximate order of selected milestones.

1977RSA

Public-key cryptography became practical through a widely influential public-key algorithm.

2001SHA-2 / SHA-512

NIST standardized the SHA-2 family, including SHA-512.

2012BIP-32

Bitcoin Improvement Proposal for hierarchical deterministic wallets.

2013BIP-39

Mnemonic code for representing wallet recovery material and deriving a seed.

2014BIP-44

Convention for multi-account hierarchical deterministic wallets.

2015SHA-3

NIST published FIPS 202, standardizing SHA-3 based on the Keccak design.

2016EIP-55

Ethereum mixed-case checksum encoding was proposed to improve address typo detection.

05 / Keccak-256 is not SHA3-256

Keccak was selected as the basis for SHA-3, but Ethereum's Keccak-256 uses a different padding/domain-separation convention from standardized SHA3-256. They both produce 256-bit digests, but the outputs are not interchangeable.

06 / What EIP-55 does—and does not do

EIP-55 hashes the lowercase hexadecimal address text with Keccak-256 and uses the hash nibbles to decide which alphabetic address characters become uppercase.

  • It helps detect many typing errors.
  • It does not encrypt or hide the address.
  • It does not change the underlying 20-byte address.
  • It is not a digital signature and does not prove ownership.

07 / Statistical properties and design goals

PrimitiveRelevant propertyImportant limitation
BIP-39 / BIP-32Deterministic reproduction of seed-derived keys.Security depends on entropy, passphrase handling and secret protection.
secp256k1Public key is deterministically derived from private scalar.Security relies on the elliptic-curve discrete logarithm problem and correct implementation.
Keccak-256Fixed 256-bit output; designed for preimage and collision resistance.Hashing does not itself provide secrecy or prove identity.
EIP-55Mixed-case pattern can detect many transcription errors.It is an error-detection convention, not a cryptographic authentication mechanism.

Different components have different statistical and security goals. A visually uniform set of outputs alone is not proof of cryptographic security; security analysis also depends on the construction, threat model and known attack resistance.
